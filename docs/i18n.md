# Internationalization

Multi language support is a launch requirement, not something to retrofit. It is
wired in from Phase 0 and there is tooling to keep it that way.

Supported: `en`, `ko`, `ja`, `zh-Hans`, `zh-Hant`, `es`, `fr`, `de`.

## How a string gets to the screen

1. It exists as a key in `shared/lang/en.json`, and in every other language file.
2. `tools/gen` turns the key set into `core/include/daemoon/str_ids.h` and the
   translations into `core/src/lang_table.c`.
3. Code refers to `DAEMOON_STR_<KEY>` and never to a literal.
4. The UI backend receives a `daemoon_str_ref_t` — an id plus its arguments — and
   calls `daemoon_strf` to render it.

The tables are compiled in rather than parsed at runtime. Parsing JSON for UI
strings would spend 3DS heap on something that never changes.

## Placeholders

Templates use `{0}`, `{1}`, ... and not printf specifiers. `{{` is a literal `{`.

The root `CLAUDE.md` calls for format placeholders rather than sentence
concatenation, and this is that, with one extra property: a translator cannot cause
undefined behaviour. Turning `"%s uses %d"` into `"%d uses %s"` — which is exactly
what translating that sentence into Japanese or Korean requires — is undefined
behaviour in C and would be a crash or worse. Reordering `{0}` and `{1}` is not.

`tools/gen` refuses to build a table where a translation's placeholder set differs
from English, and `tools/gen/gen_test.go` fails on any printf specifier appearing in
a language file.

## Adding a string

1. Add the key to `shared/lang/en.json`.
2. Add it to all seven other files.
3. `make gen`.
4. Use `DAEMOON_STR_<KEY>`.

Skipping step 2 fails `make gen`, which fails CI. There is no partially translated
state to leak into a release.

## Adding an error code

1. Add it to `shared/errors.json` with a fresh, never reused `value`.
2. Add `err.<code>` to all eight language files.
3. `make gen`.

Both the C enum and the Go constants come out of that one file, so the client and
the server cannot disagree about what a code means.

## Text handling

Everything is UTF-8. One byte is not one character and one character is not one
column, so anything that measures or cuts a string goes through
`core/src/util/utf8.c`. Truncation always lands on a code point boundary: half a
sequence renders as garbage and can fail to round trip through the server.

`daemoon_utf8_width` gives a rough column count, 2 for CJK and fullwidth ranges.
Layouts use it rather than byte counts. German and French run about 30 percent
longer than English, so no label width is hardcoded anywhere.

## Fonts

The hard part, and platform specific. See `platform/nx/CLAUDE.md` for the shared
font types and `platform/3ds/CLAUDE.md` for the region dependent system font. The
3DS decision is due in Phase 3 and its outcome belongs in `docs/fonts.md`.

## The server

The server does not localize and has no language files. It returns a code from
`shared/errors.json`; the client renders the text. That is why the same failure
reads correctly whether it happened on the network, in the archive layer, or on the
server.
